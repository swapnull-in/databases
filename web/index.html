Open the database and look inside.

Under every database is a storage engine answering two questions — where do writes go, and how do reads find them — and a replication + transaction layer that keeps copies honest. Build each from scratch and poke it: flush an LSM, crash and recover through a WAL, tune a quorum, heal a Dynamo ring, race two transactions.

Pick a lesson in the sidebar. The through-line: durability is a log, reads are a merge, and consistency is a dial (R + W > N) — everything else is a tradeoff you tune, not a default.

The LSM-tree — never write randomly to disk

Writes land in an in-memory sorted memtable; when it fills it flushes to an immutable sorted SSTable. Reads check newest→oldest. Deletes write a tombstone. Compaction merges the files, keeping the newest value and dropping tombstones.

Put keys until a flush, delete one, then compact.

memtable (RAM · newest)

The proof: every write was an in-memory insert (O(log n), no random disk I/O); a flush is one sequential pass. Reads walk layers newest→oldest — a tombstone shadows the old value. Compaction is the housekeeping tax that keeps reads and space in check. Great for write-heavy workloads.

Write-ahead log — surviving a crash

The memtable is in RAM — a crash loses it. Before acking a write, append it to a durable log (and fsync). After a crash you replay the log to rebuild the exact state. The WAL is the source of truth; the in-memory table is just a fast materialization.

memtable (RAM)

The proof: the write is durable the moment it's fsync'd to the WAL — the crash throws away RAM, and recovery replays the log to reconstruct the exact memtable. fsync is the durability point (and the throughput bottleneck every engine fights with group commit). Postgres WAL, MySQL redo log, Cassandra commitlog — same idea.

B-tree vs LSM — the three amplifications

Two opposite bets. A B-tree updates pages in place: reads are one tight path, but every write rewrites a page. An LSM appends: writes are cheap, but a read may probe many SSTables. Compaction is the knob that trades write-amp for read-amp.

9 = never compact
Drag the knob — watch write-amp and read-amp trade off.

The proof: the un-compacted LSM writes the fewest bytes (pure appends) but probes the most SSTables per read; compacting hard slashes the probes but rewrites live keys over and over (write-amp). The B-tree sits at a steady one-path read and a page-rewrite per write. Real LSMs add Bloom filters so most SSTable probes are skipped — pushing read-amp back toward 1.

Pages & the buffer pool — does the working set fit in RAM?

Disk data lives in fixed-size pages; the buffer pool is an in-memory LRU cache of hot pages. A hit is RAM-fast; a miss is a disk read ~1000× slower. So the single biggest OLTP question is whether your working set fits in the pool — and a big scan can evict it.

The proof: on a skewed workload a small pool that just holds the hot pages already hits ~90%+ (locality), and returns diminish past the working set. A full scan larger than the pool thrashes LRU — hit ratio collapses and average latency jumps toward disk speed. Hit ratio, not CPU, sets throughput; "working set fits in RAM" is the #1 OLTP predictor.

Indexes & query optimization — read the plan

The right index turns an O(N) seq scan into an O(log N) index scan. Composite indexes only help left-to-right (leftmost-prefix); a covering index answers from the index alone; and N+1 is a query-count bug a single batched IN fixes.

Replication & quorums — R + W > N

Every write copies to N replicas, but you needn't wait for all N. Require W acks per write and read from R; if R + W > N the read set and write set must overlap, so a read always sees the newest write. Below the line, reads can go stale.

R+W = 4 > N=3 ✓ overlap
Write, then read — try R+W>N vs R+W≤N.

The proof: writes hit the first W replicas, reads the last R; those subsets overlap exactly when W + R > N (pigeonhole), so a read always includes a replica with the newest version. Below the line, the read can miss the write entirely — fast, but stale. That one inequality is the dial from "eventually consistent & fast" to "strongly consistent & slower".

Dynamo-style replication — leaderless & self-healing

No primary: a key hashes to a preference list of N nodes. If one is down, hinted handoff keeps the write; when it returns, the hint is delivered. A read compares replicas and read-repair heals stale ones. Concurrent writes resolve by last-write-wins.

Put, take a node down and put again, recover, then read.

The proof: the accented nodes are user:1's preference list. With a replica down, a healthy node holds a hint so the write never fails; recovery delivers it. A read takes the newest timestamp and writes it back to any stale replica — the ring heals as a side effect of traffic. LWW keeps the latest write and silently drops a concurrent one (vector clocks would detect and merge).

Sharding — resize without a miss storm

hash(key) % N is simple but rehashes almost everything on a resize. Range, consistent-hashing, and fixed virtual shards move only ~1/N. And a hot partition needs write-sharding — no rebalancing helps a single overloaded key.

Run the resize, then flip write-sharding on the hot key.

The proof: hash-mod remaps ~80% of keys (a cache-wide miss storm); range and consistent hashing move ~1/N. Virtual shards (256 fixed vshards → nodes) move whole vshards — ~1/N of keys, with zero keys individually rehashed, which is how Vitess/Citus rebalance. A hot key still hotspots one shard until you write-shard it across suffixed sub-keys (scatter-gather on read).

Transactions — MVCC, snapshots & the lost update

MVCC keeps multiple versions per row so a transaction reads a stable snapshot — readers never block writers. But two transactions that read-then-write the same row can lose an update; a conditional write (CAS/OCC) makes the conflict surface.

Run the snapshot demo, then the lost-update demo.

The proof: under MVCC, T1's repeated reads return its snapshot even after T2 commits a new version (repeatable read). The lost update: two deposits both read 100 and write back, so one is clobbered → 130 or 150, not 180. A conditional commit (reject if the row changed since you read it) makes T2 abort and retry on the fresh value → 180. Climb the contention ladder only as high as the conflict demands.

Isolation levels — the anomaly ladder

Each level forbids one more anomaly for a price. Reproduce each with a concrete interleaving of two transactions, then read the ladder: name the anomaly you can't tolerate, and pick the weakest level that forbids it.

Banking ledger — double-entry, derived balances
